SchoolHub
Blueprint for a White-Label Digital Campus Platform
Admissions, Learning, Future Skills, Communication, and School Intelligence
Prepared for multi-campus private schools
Confidential strategy draft

1. Executive Summary
SchoolHub is a white-label digital campus platform that gives a school one branded place to run its public website, admissions funnel, parent and student portal, academic communication, learning access, future-skills programs, and leadership dashboard.
It is not positioned as a generic school management system. It is positioned as the school's digital front door and command center.
The product sits on top of an ecosystem of specialist services, including ResultsPRO, ExamsPRO, ClassroomPRO, TutorsPRO, and ScholarsNG, while keeping the user experience unified and branded to each school.
The commercial goal is simple: help schools convert more inquiries, communicate better with parents, increase student engagement, prove academic value, and open new revenue streams through future-skills and enrichment programs.
This blueprint covers the product vision, information architecture, screen inventory, user flows, service boundaries, data schema, technology stack, monetization, roadmap, go-to-market plan, risks, and financial model.
2. The Problem SchoolHub Solves
School websites often exist only as static brochure pages and do not convert visitors into leads.
Admissions follow-up is manual, inconsistent, and frequently lost in WhatsApp chats, calls, or paper forms.
Parents must jump between different systems for results, assignments, notices, fees, and transport updates.
Schools with multiple branches struggle to coordinate branding, communication, and reporting.
Future-skills programs such as coding, AI, robotics, and structured after-school learning are usually disconnected from the core school experience.
Leadership teams need one view of school health across admissions, learning, attendance, engagement, and revenue.
3. Product Vision and Positioning
SchoolHub should feel like a digital campus, not like software.
The school sees one branded experience. The platform sees multiple services.
Best positioning statement:
SchoolHub is your school's branded digital campus — connecting admissions, learning, parent engagement, future skills, and school intelligence from one place.
3.1 Product Principles
White-label first: every school's brand, tone, colors, and domain lead the experience.
Progressive activation: base plans still feel complete, while advanced modules unlock deeper value.
Outcome-based navigation: users should see tasks and results, not internal product names.
Service isolation: each specialist module owns its own data and workflows.
Shared identity and settings: authentication, roles, subscriptions, branding, and feature access are centralized.
Fast value on day one: even the base plan must support admissions, website, communication, and a coherent dashboard.

7. Core User Flows
7.1 Visitor to Enrolled Parent Flow
Visitor lands on the school website through the school’s own domain.
Visitor reads school story, academic promises, student life, and future-skills content.
Visitor clicks a conversion CTA such as Book a Tour or Start Application.
The lead is captured in AdmissionsPRO and assigned a source tag.
An automated nurture sequence sends follow-up messages and reminders.
Parent books a tour, visits campus, and submits application documents.
Assessment is scheduled if required.
School issues admission offer, collects enrollment data, and activates parent access.
7.2 Parent Daily Use Flow
Parent logs in once through the central auth service.
Parent lands on a branded dashboard with attendance, results, notices, assignments, and future-skills updates.
Parent opens a child profile to review progress and communicate with the school.
Parent receives alerts for results, fees, events, or transport updates.
Parent can return to the website, admissions area, or portal without leaving the school’s branded environment.
7.3 Teacher Workflow
Teacher logs in and sees assigned classes and pending tasks.
Teacher posts class materials or assignments in ClassroomPRO.
Teacher creates or imports assessments in ExamsPRO.
Teacher marks work or publishes scores to ResultsPRO.
Teacher sees class trends and student gaps for intervention.
7.4 Principal Workflow
Principal opens School Pulse.
System displays admissions, learning, engagement, and revenue snapshots.
Principal drills down to weak subjects, low-conversion funnel stages, or transport issues.
Principal approves campaigns, monitors growth programs, and reviews school health at a glance.

9. Microservice-Based Experience Flow
The experience should feel whole even though the backend is distributed. The rule is: the user never sees service boundaries.
The school's public domain routes requests to SchoolHub based on the host header.
SchoolHub resolves the tenant and branding profile.
SchoolHub requests feature flags and entitlements from the subscription database.
SchoolHub calls the active specialist services through APIs and aggregates the response.
The UI renders a unified dashboard and hides inactive modules.
Where a module is disabled, the interface should show a tasteful teaser or upsell, not a dead end.
9.1 Data Flow Example: Parent Dashboard
Parent logs in through central auth.
SchoolHub confirms tenant, role, and entitlements.
SchoolHub requests attendance from ClassroomPRO, results from ResultsPRO, assessments from ExamsPRO, and future-skills data from ScholarsNG.
Aggregated data is normalized into a parent-friendly response.
The UI renders a complete dashboard with school branding.

11.1 Architectural Preferences
Use an API gateway or BFF layer to compose data for the UI.
Use event-driven messages for notifications, analytics snapshots, and state changes.
Use aggressive caching for dashboard widgets that do not need real-time freshness.
Avoid letting the web app talk directly to multiple services from the browser.
12. White-Label Branding and Domain Strategy
The public experience should load from the school’s own domain, while the platform remains masked.
Public site: www.schooldomain.edu.ng or schooldomain.com.
Portal subdomain: portal.schooldomain.edu.ng or app.schooldomain.edu.ng.
SchoolHub should resolve tenant identity from host name and apply branding automatically.
The admin side can still live on a platform domain, but the school-facing experience should remain branded as the school.

24.1 Notification Rules
High-priority events go to in-app, email, and SMS where appropriate.

25. API and Integration Design
The UI should never be tightly coupled to internal service data structures. SchoolHub should consume stable APIs and present a uniform response.
Endpoint
Purpose
GET /tenant/{school}
Resolve school branding, navigation, and enabled modules from domain or slug.
GET /dashboard
Return aggregated cards for the current user role and plan.
GET /admissions/pipeline
Return leads, stages, counts, and conversion metrics.
GET /learning/progress
Return attendance, assignments, results, and class summary data.
GET /future-skills/summary
Return ScholarsNG pathways, projects, certificates, and progress.
POST /notifications/send
Dispatch messages to selected audience and log outcomes.
POST /billing/subscribe
Create or renew a subscription and unlock entitlements.
GET /school-pulse
Return leadership snapshot with cached KPIs and trend lines.
25.1 API Design Rules
Prefer response composition at the gateway layer rather than client-side stitching.
Use versioned endpoints for long-term stability.
Use idempotency keys on enrollment, billing, and notification operations.
Keep the public website fast by caching static and semi-static content aggressively.

27. Security, Privacy, and Compliance
Role-based access control across all services.
Single sign-on with secure sessions and token rotation.
Encryption in transit and at rest for sensitive school data.
Audit logs for logins, changes, exports, and billing actions.
Backups, retention policies, and disaster recovery plans.
Parent and student data segregation at tenant level.
Consent-aware messaging and permissioned communication lists.
27.1 Security Defaults
Use least privilege by default.
Separate public content from authenticated personal data.
Apply MFA for admin and leadership accounts where possible.
Use secure file storage for results, certificates, and admissions documents.
